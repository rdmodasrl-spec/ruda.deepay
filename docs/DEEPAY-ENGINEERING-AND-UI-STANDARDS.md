# DEEPAY 项目永久开发铁规

## 工程质量标准 × 高端 UI 设计标准 × 交付验收制度

适用范围：平台运营后台、个人钱包 Web/移动端、商户后台、代理后台、钱包 API、账务系统及区块链模块。

> 本文描述长期工程和产品标准，不代表相关功能已经实现。产品范围和第一阶段验收基线见 [DEEPAY 产品规格](./DEEPAY-PRODUCT-SPEC-V1.md)。

## 1. 最高开发原则

DEEPAY 必须达到正式商业金融科技产品的质量：

1. 功能真实可用，不能只做界面。
2. 每个按钮都必须触发真实业务动作。
3. 页面必须连接真实 API 和数据库。
4. 钱包余额来自真实账务系统，交易状态来自真实业务状态。
5. 不用假数据、假统计或假余额冒充正式功能。
6. 不为了 UI 效果破坏原有业务逻辑。
7. 不为赶进度留下大量空页面和无效入口。
8. 不重复创建已有功能。
9. 未检查前不得擅自修改 DaxPay 核心。
10. 所有端共享统一业务规则。
11. UI、API、数据库和权限形成完整闭环。

功能完成的判断标准是：真实操作能够完整成功，而不是页面能够打开。

## 2. 架构与原系统保护

### 2.1 先检查，后开发

确认并记录：

- Git 仓库地址、当前分支和提交版本。
- 后端与前端技术栈。
- 数据库结构和已有 API。
- 登录及权限系统。
- 已有 DaxPay 支付模块。
- 已部署的运行环境。

只进行一次必要的源码现状检查，形成清晰模块清单。已有功能直接复用，不重复开发。未经确认不得大面积删除、重构、迁移或覆盖原有代码。

### 2.2 模块边界

DEEPAY 业务模块规划为：

- 用户及身份。
- 钱包及资产。
- 支付收款。
- 区块链。
- RUD Token。
- 商户管理。
- 代理管理。
- 佣金结算。
- 财务账务。
- 安全风控。
- 平台管理。

模块通过明确服务接口通信。钱包账务不与支付订单混成一个模块；RUD 不依赖普通用户余额字段；代理佣金不得直接修改钱包余额。

### 2.3 DaxPay 保护要求

DaxPay 已有支付、退款、转账和分账能力优先复用。新增功能不得破坏原支付接口、支付订单、退款流程、回调机制、商户数据、权限控制或数据库结构。

修改前确认影响范围。数据库变更提供迁移方案、回滚方案和数据兼容性检查。优先经 API 集成；修改 DaxPay 核心时遵守 LGPL-3.0-or-later 及相关组件许可义务。

## 3. 高端 UI 设计标准

### 3.1 视觉定位

采用 **Premium Fintech × Modern Minimal × Precision Interface**。视觉目标：高级、极简、精致、干净、稳重、清晰、专业、有层次、有空间感、操作直接。

避免传统银行后台和普通商城后台的观感。

### 3.2 颜色

以黑、白、灰为主：柔和浅灰白页面背景、白色内容区、深色侧边栏、近黑主文字、中灰次要文字、极浅灰边框和分隔线。主要操作使用黑色；成功、警告、错误分别使用克制的绿、橙、红，并只传递真实业务状态。

禁止默认金色主题、大面积彩色渐变、五颜六色功能卡片、蓝紫色科技光效、模块各自使用不同主题及无意义装饰。

### 3.3 字体、数据与空间

- 使用现代、清晰、专业的无衬线字体。
- 页面标题层级清晰；正文不能过小；避免整页超大字体。
- 数字使用等宽数字或对齐方式；金额易读，资产符号与金额分开。
- 余额、交易金额和订单编号应具备清晰视觉层级。
- 合理使用留白、内容分组、行距、间距、对齐和表格密度。
- 避免页面堆满卡片；桌面端控制内容宽度，不让文字区域过宽。
- 手机端按设备重新组织布局，不能只缩小桌面页面。

### 3.4 移动端与渐进式 Web App

个人钱包 Web 端采用移动端优先的响应式设计，并按 PWA 方式交付，使其在支持的手机浏览器中可添加到主屏幕，尽量提供连贯、接近原生应用的使用体验。该要求不等于开发原生 iOS/Android 客户端，也不意味着已承诺应用商店上架。

- 生产环境必须使用 HTTPS；本地开发可使用受支持的安全开发环境。
- 提供正确的 Web App Manifest、应用名称、图标、主题色和独立窗口显示配置；仅在需要时添加 Service Worker。
- 手机布局针对窄屏重新组织信息层级、底部/顶部导航、表单、列表及主要操作，不得只缩小桌面组件。
- 尊重系统安全区域和刘海屏；重要触控目标尺寸适宜，页面滚动、键盘弹起、返回导航和加载/错误反馈均需实机验证。
- 优先保证钱包核心流程易理解、状态反馈明确；动画和触觉反馈只能作为渐进增强，不得阻塞操作或作为唯一反馈。
- 离线时只允许使用经过审查的非敏感应用外壳资源。不得缓存或离线展示余额、交易详情、身份信息、访问凭证、私钥或签名材料；不得离线执行/排队资金操作并伪装成成功。恢复联网后需重新从服务端获取权威状态。
- PWA 安装能力不能取代认证、授权、交易确认、风控和服务端账务校验。
- 验证常见手机尺寸与桌面视口、主要移动浏览器及安装后模式；记录真实设备或浏览器测试结果。截图不能替代触控和流程测试。

### 3.5 卡片和按钮

卡片统一使用适度圆角、细腻边框、轻微或无阴影、清晰标题和合理留白。按钮短而清晰，避免整行长按钮；主次操作明确，图标与文字协调，同一功能跨页面样式一致。

禁止重复堆叠装饰卡片，禁止同一功能在同一页面出现多个重复入口。

## 4. 页面标准

### 4.1 钱包首页

首页应让用户立即看到资产及常用操作：

- 顶部：DEEPAY Logo、账户头像、通知、安全状态。
- 资产主区域：总资产估值、余额显示/隐藏、EUR/USDT/USDC/BTC/RUD 分布和最近资产变化。
- 常用操作：充值、提现、转账、收款。
- 下方：最近交易、资产列表和查看全部交易。

不堆积大量功能卡片。余额必须来自钱包账务；总资产估值必须注明币种、价格来源和更新时间，不得直接相加不同币种余额。

### 4.2 资产详情页

每个资产独立展示币种名称、Logo、余额、可用/冻结/待确认金额，以及充值、提现、转账、收款和历史记录操作。

USDT、USDC 明确显示网络；同币种不同网络分别展示。

### 4.3 交易页面

交易列表每条记录展示类型、币种、金额、时间、状态和交易编号；点击进入详情。详情按适用情况显示交易金额、手续费、网络、区块链交易哈希、收款地址、确认数、交易状态和关联账务记录。

> 用户提供的原始规范在此处截断（原文停在“不要用大卡片展示每一条普…”）。交易列表后续视觉细节及其他页面规范待补充；在补充前不自行推定原文未提供的要求。

## 5. 设计辅助工具使用约定

Impeccable（[pbakaus/impeccable](https://github.com/pbakaus/impeccable)）可用于辅助编码代理理解设计意图、迭代已有页面，以及检查可用性、响应式表现、可访问性和视觉一致性。它不是 PWA 框架、支付/钱包实现或安全审计工具，也不能替代浏览器、真实设备、功能测试及人工验收。

前端页面开发时可按项目和当前编码工具支持情况使用其设计命令（例如针对具体页面进行 `critique`、`audit`、`adapt`、`polish`）；应缩小目标逐页迭代，并以本规范、产品规格及经确认的品牌系统为准。若工具生成或更新 `PRODUCT.md`、`DESIGN.md` 等上下文文件，先审阅差异再纳入，不得让工具自动覆盖本规范或无范围地重写项目。

安装前确认工具当前安装方式、作用范围和将新增/修改的文件；只在需要开展前端设计工作时引入，不将其作为生产运行依赖。工具报告只能作为问题线索，所有发现须结合实际页面验证，金融业务正确性及安全性另行按对应测试和审查流程验收。
