## 1. 项目定位与原则

DEEPAY 是独立数字钱包及支付平台，不是 RUDA 的附属钱包，也不局限于 RUDA 商户。未来，符合平台要求的个人、企业、商户和代理均可申请使用。

平台目标：

1. 为个人用户提供 DEEPAY 钱包，支持充值、接收、转账和付款。
2. 规划 EUR、USDT、USDC、BTC 及 RUD 资产支持。
3. 规划真正部署在区块链上的 RUD Token。
4. 为商户提供收款及支付接入能力。
5. 代理通过发展商户获得基于真实交易和实际可分配收入的佣金。
6. 平台统一核算佣金、审核结算并向代理付款。
7. 为未来第三方市场接入预留接口，但不承诺上币或公开交易。

必须明确区分两套互不混同的余额体系：

1. **平台余额（DEEPAY Account Balance）**：由 DEEPAY 后端复式账本管理，覆盖平台内部法币余额、内部转账、商户付款、退款、手续费和结算。平台账本中的数字资产余额也属于平台账本/托管体系；即使资产代码是 USDT 或 TRX，也不代表用户控制私钥或拥有自托管钱包。
2. **自托管钱包余额（Self-Custody Wallet）**：由用户控制私钥并在用户设备或其选择的钱包中签名，真实余额及交易状态来自对应区块链。平台不得持有或返回用户私钥、助记词，不得通过平台账本余额冒充链上余额。

两套余额必须分别展示、分别记账和分别查询。只有经过授权并具备明确资产交割、费用和对账规则的兑换或资金转移流程，才可在两套体系之间转移价值；不能通过直接修改另一套余额完成“兑换”。当前代码中的 TRON 充值/提现属于平台账本和托管服务流程，不是自托管钱包功能。自托管钱包尚未接入，不能对用户宣称已支持。

RUD 是独立链上资产，不是可由后台任意改写的余额，也不是稳定币。

## 2. 系统组成及用户端

DEEPAY 采用独立业务系统与 DaxPay 支付底座组合的架构，形成四类用户端。

### 2.1 个人钱包端

个人钱包 Web 端按渐进式 Web App（PWA）建设，手机浏览器使用时应尽可能接近原生应用体验，并提供“添加到主屏幕/安装”能力。PWA 不等于原生 iOS/Android App；当前第一阶段交付范围是可安装的移动端优先 Web 应用，不承诺 App Store 或 Google Play 上架。

钱包首页规划展示：

- 总资产估值、估值币种、价格来源和更新时间。
- EUR、USDT、USDC、BTC、RUD 余额及最近交易。
- 充值、转账、收款、付款、提现、资产记录和安全中心入口。

每项资产必须明确显示网络。同名资产在不同网络上不得被误认为同一资产。

手机端须适配常见窄屏和安全区域，使用适合触控的导航、表单及反馈；桌面端仍保持完整可用。PWA 的离线能力仅限应用外壳等非敏感静态资源；余额、交易明细、身份信息及任何资金操作均须在线从授权 API 获取或提交，不得因离线缓存显示过期余额或把离线操作表现成成功。

### 2.2 商户端

规划功能：

- 商户注册、资料管理及多币种收款配置。
- 收款链接、动态收款二维码和支付订单。
- 订单及交易记录、退款申请、结算记录。
- API 密钥管理和财务报表。

商户只能选择平台实际开放的资产和支付通道。

### 2.3 代理端

规划功能：

- 邀请码、二维码、下级代理及商户拓展。
- 商户管理和真实交易统计。
- 佣金明细、待结算/已结算佣金、提现记录和结算账单。

代理佣金只能由真实成功交易及平台实际可分配收入产生，不得按邀请或注册人数支付。

### 2.4 平台运营端

规划后台模块：

- 用户、商户和代理管理。
- 法币支付、数字资产、钱包账务和 RUD Token 管理。
- 充值、提现审批、交易和代理佣金管理。
- 财务结算、风险控制、区块链网络及合约管理。
- 审计日志和系统配置。

## 3. 资产与币种配置

第一阶段定义五类资产：EUR（模拟法币支付和记账）、USDT、USDC（测试网充值及支付）、BTC（Bitcoin 测试网络充值及转账）、RUD（测试生态代币）。

币种配置中心至少记录：

- 资产名称、符号、资产类型。
- 区块链网络、适用时的 Chain ID、适用时的合约地址。
- 精度、最低充值金额、最低提现金额和手续费。
- 充值确认数。
- 是否允许充值、提现、内部转账、商户收款和用户显示。

要求：

- USDT、USDC 按具体网络分别配置，不得仅以币种名称识别。
- BTC 使用原生 Bitcoin 网络，不得与包装 BTC 混淆。
- 正式合约地址必须通过发行方或可信官方渠道核实。
- 未确定的网络、发行方、精度、额度、费用及地址不得擅自填成正式配置。

## 4. 钱包、账户和账务

### 4.1 钱包账户

用户注册后创建钱包账户，规划覆盖 EUR、USDT、USDC、BTC、RUD。链上资产由独立钱包地址或受托服务商提供的用户专属充值地址/识别方式承载。

#### 平台账本账户与自托管钱包边界

- **DEEPAY 平台账本账户**：账户余额和可用、待确认、冻结、预留等状态以 DEEPAY 后端复式账本为准。当前 TRON USDT/TRX 充值和提现均属于此类平台托管资产流程；提现申请冻结的是平台账本余额，链上执行由已配置的托管服务处理。
- **用户自托管钱包**：属于另一套独立账户。私钥由用户保管、签名在用户设备或用户控制的钱包完成，链上余额由网络查询得到。该能力只有在密钥、设备签名、链上读取和交易广播功能实际交付后才能标记为可用。
- 资产代码相同不表示余额可以合并。例如平台托管账本中的 USDT 与自托管钱包中 Ethereum、TRON 或 Polygon 网络上的 USDT，均需按资产来源和网络分别展示、记账及对账。
- 未实现的跨体系兑换/划转不得创建“成功”流水，也不得只调整平台数据库余额。

每种资产分别记录 Available（可用）、Pending（待确认）、Frozen（冻结）、Reserved（已预留）和 Withdrawn（已提现或转出）等余额状态。所有金额以整数最小单位存储，禁止使用浮点数进行资产金额计算。

### 4.2 复式记账要求

钱包账务采用复式记账。例如用户 A 向用户 B 转账 10 USDT，应在同一事务内完成 A 的借记和 B 的贷记，确保账务平衡，不能只修改一方。

账务必须：

- 不可直接删除；余额不得由后台普通输入框直接修改。
- 每笔交易有唯一业务编号，并支持幂等处理。
- 支持冲正、对账和关联原始交易。
- 追踪操作人员、审批人及操作审计。
- 财务调整只能通过经审批的会计分录完成。

区块链充值须区分待确认、确认中、已到账和异常状态。不得仅凭前端返回成功就入账。

## 5. 充值、提现与托管安全

### 5.1 充值流程

1. 用户选择资产和网络。
2. 系统提供与所选网络匹配的充值地址或识别方式。
3. 区块链服务监测交易。
4. 达到配置的确认数后，核对网络、金额及交易哈希。
5. 创建不可篡改的账务流水并更新余额。

### 5.2 提现流程

1. 用户填写提现地址和金额。
2. 检查可用余额。
3. 执行安全验证及风险检查。
4. 按授权策略审批。
5. 由合规托管服务签名并广播交易。
6. 追踪链上确认并更新提现状态和账务。

正式环境不得将客户私钥存放在普通数据库、前端代码或服务器配置文件中。正式客户资金不得放在开发人员的测试钱包或个人钱包中。

## 6. RUD Token

### 6.1 代币定义

| 属性 | 规划 |
| --- | --- |
| 名称 / 符号 | RUD Token / RUD |
| 发行主体 | 待确定的正式法律主体 |
| 标准 | ERC-20 |
| 网络 | 经测试和评估后确定 |
| 测试阶段 | 测试网代币 RUD-TEST |
| 正式用途 | DEEPAY 生态功能及平台服务权益，须经法律及合规评估 |

RUD 不是 EUR、USDT 或 USDC 的替代稳定币。不得在没有相应监管和发行安排的情况下承诺固定欧元价格、固定收益、保本回购或投资回报。

### 6.2 合约要求

建议使用经过广泛使用和安全审查的 OpenZeppelin ERC-20 实现。第一版规划包括名称、符号、精度、初始发行量、转账、余额/总供应量查询和事件日志；紧急暂停机制只有在安全与治理设计确认后启用。

优先采用固定总量、清楚披露的发行设计。若未来确需增发，必须事先定义最大供应量、增发条件、权限主体和多签审批机制。正式代币不应随意采用可升级合约，也不得保留不受限制的后台铸币权限。

正式部署前，必须经公司正式批准并披露总发行量、团队/生态/商户/社区用途、流动性安排、锁定与解锁计划、资金管理主体和多签管理人。本文不预设发行数量或分配比例。

### 6.3 生态用途与市场

第一阶段仅测试钱包显示、测试网转账、收款、交易记录和账户对账。未来可能研究商户服务权益、平台服务费抵扣、生态奖励、商户活动、会员权益及经合规批准的生态内支付用途。

RUD 不得用于掩盖平台真实欠款、虚增用户资产或虚增代理佣金。第一阶段不开发公开交易所，只预留合约信息、供应量/流通量、区块链浏览器、行情数据、交易平台适配、上币资料及风险披露接口。满足发行披露、白皮书和平台要求前，不开放公开交易；不得伪造交易量或流动性，也不承诺能够上市。

## 8. DaxPay 集成边界

DaxPay 保留为独立支付引擎。DEEPAY 不重做 DaxPay 已有能力。

**DaxPay 负责：** 法币支付、支付订单、退款、支付查询、支付回调、现有通道、支付转账及分账能力。

**DEEPAY 新增：** 钱包账户、多币种资产、链上充值/提现、内部转账、RUD Token、钱包账本、代理佣金/结算、财务对账、合规和风控。

DEEPAY 通过现有 `/unipay/*` RSA 签名接口与 DaxPay 业务系统连接。优先 API 集成，采用独立业务模块或模块化服务，避免大面积修改支付核心。修改 DaxPay 本身须遵守 LGPL-3.0-or-later 及相关组件许可，并处理相应开源义务。

## 9. 代理与佣金结算

代理关系规划为平台 → 总代理 → 一级代理 → 二级代理 → 商户；后台支持可配置层级，默认按三级体系设计并保留扩展能力。

可分配收入 = 平台实际收入 − 支付通道成本 − 退款及拒付损失 − 风险准备金 − 其他约定成本。

佣金规则：

- 每笔交易最多计佣一次，不得重复分润。
- 退款及拒付自动冲减佣金。
- 代理仅可访问授权范围内的数据。
- 佣金支持待结算、冻结、可结算、已结算、已冲正状态。

结算流程：订单真实完成 → 支付平台确认交易 → 佣金引擎核算 → 进入待结算 → 退款/风险窗口核查 → 生成结算单 → 管理员审核 → 平台付款 → 保存银行或链上凭证 → 代理端显示已付款。

第一阶段以合规银行转账为代理付款方式；加密资产付款必须通过获得授权的服务商。招募代理、收取入门费或单纯发展下级人数不得成为佣金来源。

## 13. 分阶段实施

### 第一阶段：内部测试版（当前范围）

目标是跑通真实业务闭环，而不是仅展示页面：

1. DEEPAY 用户注册和登录。
2. 多资产钱包账户及内部账务。
3. 测试网 USDT、USDC 和 Bitcoin 测试网络。
4. RUD-TEST 测试合约。
5. 模拟法币支付和 DaxPay 接口集成。
6. 商户测试账户及测试订单。
7. 代理关系、佣金计算和结算审批。
8. 管理后台和财务报表。

测试代币不得有公开市场价值，不得允许与真实资产兑换。

### 第二阶段：合规准备与小范围正式试运营

前置条件包括确定经营主体、完成法律分类、确认支付及加密资产服务许可边界、接入符合资质的银行/支付机构/CASP、完成 KYC/KYB/AML/风险监控/数据保护、完成合约审计及财务对账、建立客户支持和风险处置机制。所有必要条件满足前，不开启公众充值、提现及真实链上托管。

### 第三阶段：RUD 正式部署

通过正式发行方案、确定发行主体/总供应量/网络、发布审核后的代币资料、部署及验证正式合约、建立官方合约信息页面，并仅开放批准范围内的生态功能。

### 第四阶段：公开市场规划

完成公开交易法律评估，准备适用的 MiCA 白皮书和披露材料，评估并尽调第三方交易平台，在满足条件后再申请接入。

3. 内部账户转账成功。

5. USDT 测试网络充值成功。
6. USDC 测试网络充值成功。
7. Bitcoin 测试网络充值成功。
